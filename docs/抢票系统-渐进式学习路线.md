# 抢票系统 - 渐进式学习与迭代优化路线

> 从刚毕业的 CRUD 水平开始，逐步迭代优化，每个阶段解决一个真实问题，每个优化都有对应的技术点。

---

## 阶段零：需求分析

### 核心功能

1. **用户模块**：注册、登录、个人信息
2. **票务模块**：创建票/活动、查看票务信息
3. **抢票模块**：用户抢票、下单、支付（模拟）
4. **任务调度**：订单超时自动取消、定时放票

### 业务场景

- 用户注册登录后，可以查看可抢的票务活动
- 活动有开始时间、结束时间、总票数
- 用户在活动时间内可以抢票，每人限购 N 张
- 抢票成功后生成订单，订单 30 分钟未支付自动取消
- 取消后票数回滚，可以重新被抢

```java
// 抢票接口 - 最原始的版本
@PostMapping("/grab")
public Result grabTicket(@RequestParam Long activityId, 
                         @RequestParam Long userId,
                         @RequestParam Integer quantity) {
    // 1. 查询活动信息
    TicketActivity activity = ticketService.getById(activityId);
    
    // 2. 判断活动是否在时间内
    if (activity.getStartTime().after(new Date()) || 
        activity.getEndTime().before(new Date())) {
        return Result.error("活动不在有效期内");
    }
    
    // 3. 判断库存是否充足
    if (activity.getAvailableStock() < quantity) {
        return Result.error("库存不足");
    }
    
    // 4. 扣减库存
    activity.setAvailableStock(activity.getAvailableStock() - quantity);
    ticketService.updateById(activity);
    
    // 5. 创建订单
    Order order = new Order();
    order.setOrderNo(generateOrderNo());
    order.setUserId(userId);
    order.setActivityId(activityId);
    order.setQuantity(quantity);
    order.setStatus(0); // 待支付
    order.setExpireTime(calculateExpireTime()); // 30分钟后过期
    orderService.save(order);
    
    return Result.ok("抢票成功", order.getOrderNo());
}
```

### 这个阶段的问题

跑是跑起来了，但有以下问题：

1. **超卖问题**：两个人同时抢最后一张票，都判断库存充足，都扣减成功，结果卖出去两张
2. **性能问题**：每次请求都查数据库，数据库扛不住
3. **没有并发控制**：没有任何锁机制
4. **订单过期没处理**：30分钟不支付应该自动取消，但现在没实现

## 阶段二：解决超卖（并发入门）

> 目标：解决最致命的超卖问题

### 方案对比

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **悲观锁** | `SELECT ... FOR UPDATE` | 简单直接 | 性能差，锁住整行 |
| **乐观锁** | 版本号机制 | 性能好 | 冲突多时重试成本高 |
| **数据库唯一索引** | `user_id + activity_id` 唯一 | 简单 | 只能防重复，不能防超卖 |
| **Redis 分布式锁** | `SETNX` | 性能好，支持分布式 | 需要引入 Redis |

### 实现：悲观锁版本

```java
// Mapper 加锁查询
@Select("SELECT * FROM ticket_activity WHERE id = #{id} FOR UPDATE")
TicketActivity selectForUpdate(Long id);

// Service 使用锁
public synchronized Result grabTicket(Long activityId, Long userId, Integer quantity) {
    // 加锁查询
    TicketActivity activity = ticketMapper.selectForUpdate(activityId);
    
    if (activity.getAvailableStock() < quantity) {
        return Result.error("库存不足");
    }
    
    // 扣减库存
    activity.setAvailableStock(activity.getAvailableStock() - quantity);
    ticketMapper.updateById(activity);
    
    // ... 创建订单
}
```

### 实现：乐观锁版本

```sql
-- 表加版本号字段
ALTER TABLE ticket_activity ADD COLUMN version INT DEFAULT 0;
```

```java
// MyBatis-Plus 乐观锁插件
@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        return interceptor;
    }
}

// Entity 加 @Version 注解
@Version
private Integer version;

// Service 重试机制
public Result grabTicket(Long activityId, Long userId, Integer quantity) {
    int retryCount = 3;
    while (retryCount > 0) {
        TicketActivity activity = ticketService.getById(activityId);
        
        if (activity.getAvailableStock() < quantity) {
            return Result.error("库存不足");
        }
        
        activity.setAvailableStock(activity.getAvailableStock() - quantity);
        int rows = ticketMapper.updateById(activity); // 乐观锁：version 不匹配会返回 0
        
        if (rows > 0) {
            // 扣减成功，创建订单
            createOrder(activityId, userId, quantity);
            return Result.ok("抢票成功");
        }
        
        // 更新失败，重试
        retryCount--;
    }
    return Result.error("系统繁忙，请重试");
}
```

### 这个阶段学到的

- 并发问题的本质：多个线程同时读写共享资源
- 悲观锁 vs 乐观锁的适用场景
- synchronized 的局限性（单机有效，分布式无效）

## 阶段三：引入缓存（性能优化）

> 目标：解决数据库压力问题，提升响应速度

### 问题：每次请求都查数据库

```
用户抢票 → 查活动信息 → 判断库存 → 扣减库存 → 创建订单
              ↑
         每次都查数据库，1000个请求就是1000次查询
```

### 方案：Redis 缓存活动信息

```java
// 活动创建时，同步到 Redis
public void createActivity(TicketActivity activity) {
    ticketMapper.insert(activity);
    
    // 缓存到 Redis
    String key = "ticket:activity:" + activity.getId();
    redisTemplate.opsForValue().set(key, JSON.toJSONString(activity));
}

// 抢票时，先查缓存
public Result grabTicket(Long activityId, Long userId, Integer quantity) {
    String key = "ticket:activity:" + activityId;
    String json = (String) redisTemplate.opsForValue().get(key);
    
    TicketActivity activity;
    if (json != null) {
        activity = JSON.parseObject(json, TicketActivity.class);
    } else {
        activity = ticketService.getById(activityId);
        redisTemplate.opsForValue().set(key, JSON.toJSONString(activity));
    }
    
    // 判断库存（用缓存中的库存）
    if (activity.getAvailableStock() < quantity) {
        return Result.error("库存不足");
    }
    
    // ... 后续逻辑
}
```

### 问题：缓存和数据库不一致

```
缓存中库存是 100
数据库扣减后库存是 99
但缓存还是 100，导致超卖
```

### 解决：先更新数据库，再删除缓存

```java
public synchronized Result grabTicket(Long activityId, Long userId, Integer quantity) {
    // 1. 数据库扣减库存
    int rows = ticketMapper.deductStock(activityId, quantity);
    if (rows == 0) {
        return Result.error("库存不足");
    }
    
    // 2. 删除缓存（让下次查询重新加载）
    String key = "ticket:activity:" + activityId;
    redisTemplate.delete(key);
    
    // 3. 创建订单
    createOrder(activityId, userId, quantity);
    return Result.ok("抢票成功");
}
```

### 进阶：Redis 预扣减库存

```java
// 活动开始时，把库存加载到 Redis
public void preloadStock(Long activityId) {
    TicketActivity activity = ticketService.getById(activityId);
    String stockKey = "ticket:stock:" + activityId;
    redisTemplate.opsForValue().set(stockKey, activity.getAvailableStock());
}

// 抢票时，直接在 Redis 扣减
public Result grabTicket(Long activityId, Long userId, Integer quantity) {
    String stockKey = "ticket:stock:" + activityId;
    
    // Redis 原子扣减
    Long stock = redisTemplate.opsForValue().decrement(stockKey, quantity);
    
    if (stock < 0) {
        // 库存不足，回滚
        redisTemplate.opsForValue().increment(stockKey, quantity);
        return Result.error("库存不足");
    }
    
    // 扣减成功，异步创建订单
    orderService.createOrderAsync(activityId, userId, quantity);
    return Result.ok("抢票成功");
}
```

### 这个阶段学到的

- 缓存的使用场景和常见问题（穿透、击穿、雪崩）
- 缓存一致性策略（Cache Aside、Read/Write Through）
- Redis 原子操作的重要性

## 阶段四：异步处理（消息队列）

> 目标：提升吞吐量，削峰填谷

### 问题：同步创建订单太慢

```
抢票成功 → 创建订单 → 扣减库存 → 返回结果
              ↑
         数据库写入耗时 200ms，用户等着
```

### 方案：用消息队列异步处理

```java
// 抢票接口只负责扣减库存，发消息
public Result grabTicket(Long activityId, Long userId, Integer quantity) {
    // 1. Redis 预扣减
    Long stock = redisTemplate.opsForValue().decrement(stockKey, quantity);
    if (stock < 0) {
        redisTemplate.opsForValue().increment(stockKey, quantity);
        return Result.error("库存不足");
    }
    
    // 2. 发送消息到 MQ
    OrderMessage msg = new OrderMessage(activityId, userId, quantity);
    rabbitTemplate.convertAndSend("order.exchange", "order.create", msg);
    
    return Result.ok("抢票成功，请在订单中查看");
}

// 消费者异步创建订单
@RabbitListener(queues = "order.create.queue")
public void handleOrderMessage(OrderMessage msg) {
    // 创建订单
    Order order = new Order();
    order.setOrderNo(generateOrderNo());
    order.setUserId(msg.getUserId());
    order.setActivityId(msg.getActivityId());
    order.setQuantity(msg.getQuantity());
    order.setStatus(0);
    order.setExpireTime(calculateExpireTime());
    orderMapper.insert(order);
}
```

### 这个阶段学到的

- 消息队列的使用场景（异步、解耦、削峰）
- 消息丢失、重复消费、顺序消息等问题
- 最终一致性的概念

## 阶段五：任务调度（定时任务）

> 目标：实现订单超时自动取消

### 方案对比

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **定时轮询** | 每分钟扫一次过期订单 | 简单 | 实时性差，数据库压力大 |
| **延迟队列** | RabbitMQ 延迟消息 | 实时性好 | 需要 RabbitMQ |
| **Redis 过期回调** | Key 过期事件 | 简单 | 不可靠，可能丢失 |
| **时间轮** | Netty HashedWheelTimer | 性能好 | 实现复杂 |

### 实现：RabbitMQ 延迟队列

```java
// 下单后，发送延迟消息
public void createOrder(...) {
    Order order = ...;
    orderMapper.insert(order);
    
    // 发送延迟消息，30分钟后触发
    rabbitTemplate.convertAndSend(
        "order.delay.exchange",
        "order.timeout",
        order.getOrderNo(),
        message -> {
            message.getMessageProperties().setDelay(30 * 60 * 1000); // 30分钟
            return message;
        }
    );
}

// 消费者处理超时订单
@RabbitListener(queues = "order.timeout.queue")
public void handleTimeoutOrder(String orderNo) {
    Order order = orderMapper.selectByOrderNo(orderNo);
    
    // 如果订单还是待支付状态，说明没支付，需要取消
    if (order != null && order.getStatus() == 0) {
        // 取消订单
        order.setStatus(2);
        orderMapper.updateById(order);
        
        // 回滚库存
        ticketService.rollbackStock(order.getActivityId(), order.getQuantity());
    }
}
```

### 实现：定时轮询（简单版）

```java
// Spring Task 定时任务
@Scheduled(fixedRate = 60000) // 每分钟执行一次
public void cancelTimeoutOrders() {
    Date now = new Date();
    
    // 查询所有过期的待支付订单
    List<Order> timeoutOrders = orderMapper.selectList(
        new QueryWrapper<Order>()
            .eq("status", 0)
            .lt("expire_time", now)
    );
    
    for (Order order : timeoutOrders) {
        // 取消订单
        order.setStatus(2);
        orderMapper.updateById(order);
        
        // 回滚库存
        ticketService.rollbackStock(order.getActivityId(), order.getQuantity());
    }
}
```

- 定时任务的几种实现方案
- 延迟队列的原理和使用
- 任务调度的可靠性问题（任务丢失、重复执行）

## 阶段六：分布式锁（进阶并发）

> 目标：解决分布式环境下的并发问题

### 问题：synchronized 在分布式环境下失效

```
服务 A: synchronized 锁住方法 → 只锁住 A 的 JVM
服务 B: synchronized 锁住方法 → 只锁住 B 的 JVM
A 和 B 可以同时执行，还是会超卖
```

### 方案：Redis 分布式锁

```java
// 简易版分布式锁
public boolean tryLock(String key, String value, long expireTime) {
    Boolean result = redisTemplate.opsForValue()
        .setIfAbsent(key, value, expireTime, TimeUnit.SECONDS);
    return result != null && result;
}

public void unlock(String key, String value) {
    // 只释放自己的锁（Lua 脚本保证原子性）
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                    "return redis.call('del', KEYS[1]) else return 0 end";
    redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
        Collections.singletonList(key), value);
}

// 抢票使用分布式锁
public Result grabTicket(Long activityId, Long userId, Integer quantity) {
    String lockKey = "lock:ticket:" + activityId;
    String lockValue = UUID.randomUUID().toString();
    
    try {
        // 加锁
        if (!tryLock(lockKey, lockValue, 10)) {
            return Result.error("系统繁忙，请重试");
        }
        
        // 业务逻辑
        return doGrabTicket(activityId, userId, quantity);
        
    } finally {
        // 释放锁
        unlock(lockKey, lockValue);
    }
}
```

### 进阶：Redisson 分布式锁

```java
// 使用 Redisson
RLock lock = redissonClient.getLock("lock:ticket:" + activityId);
try {
    // 加锁，最多等待 5 秒，锁持有 10 秒自动释放
    if (lock.tryLock(5, 10, TimeUnit.SECONDS)) {

        lock.unlock();
    }
}
```

## 阶段八：高可用（系统稳定性）

> 目标：系统挂了怎么办

### 1. 限流

```java
// 令牌桶限流
@Aspect
@Component
public class RateLimitAspect {
    private LoadingCache<String, RateLimiter> cache = CacheBuilder.newBuilder()
        .build(new CacheLoader<String, RateLimiter>() {
            @Override
            public RateLimiter load(String key) {
                return RateLimiter.create(100); // 每秒 100 个请求
            }
        });
    
    @Around("@annotation(rateLimit)")
    public Object around(ProceedingJoinPoint point, RateLimit rateLimit) throws Throwable {
        String key = point.getSignature().toShortString();
        RateLimiter rateLimiter = cache.get(key);
        
        if (!rateLimiter.tryAcquire()) {
            throw new RuntimeException("请求太频繁，请稍后重试");
        }
        
        return point.proceed();
    }
}
```
