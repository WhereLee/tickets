# 阶段一总结：基础版本（CRUD + 抢购流程）

## 一、本阶段做了什么

### 功能清单
- **用户模块**: 注册、登录（明文密码，后续阶段加密）
- **活动模块**: 创建活动、查询活动列表、查询进行中活动
- **抢购模块**: 抢购（核心）、支付订单、取消订单（回滚库存）、查询订单
- **防重复**: grab_record 表 + 唯一索引 (user_id, activity_id)

### 技术栈
| 组件 | 选型 | 说明 |
|------|------|------|
| 框架 | Spring Boot 2.7.18 | Java 17 |
| ORM | MyBatis-Plus 3.5.3 | BaseMapper + @Update 自定义 SQL |
| 数据库 | MySQL 8.0 | 4 张表（user/activity/grab_order/grab_record） |
| 测试 | JUnit 5 + Spring Boot Test | 17 个测试用例 |
| 压测 | JMeter 5.6.3 | .jmx 脚本 + 命令行模式 |

### 核心抢购流程（OrderService.grab）
```
1. 查活动（存在性）
2. 校验时间窗口（未开始/已结束）
3. 查抢购记录（是否已参与）← 存在竞态
4. 校验限购数量
5. 查库存是否充足 ← 多余检查（竞态下不可靠）
6. 扣减库存（原子 UPDATE + 条件）← 真正防超卖的关键
7. 创建订单（30 分钟过期）
8. 插入抢购记录（唯一索引兜底）
```

## 二、验证结果

### 单元测试
- 17/17 通过（UserService 5 + ActivityService 5 + OrderService 7）
- 覆盖: 正常路径、重复抢购、超限购、活动不存在、库存不足、支付、取消回滚

### 接口验证
- 登录/注册/活动列表/抢购/查单/支付/取消 全部通过
- 异常分支返回预期错误信息

### 压测结果（基线）
- 场景: 100 并发抢购 activity=1（库存 100），Ramp-Up=0
- **吞吐量: 61.9 req/s**
- **平均响应: 1189 ms**（885 ~ 1459）
- 错误率: 0%
- 业务结果: 65 成功 / 35 拒绝（随机用户碰撞），库存 100 → 剩余 35 + 订单 65，**无超卖**

## 三、发现的问题（详见 development-log.md）

1. **性能差**: 平均响应 1189ms，TPS 61.9 —— 每次抢购 4+ 次数据库交互，并发全部排队等行锁
2. **异常提示不友好**: 并发下重复抢购触发唯一索引冲突 → 返回"系统异常"而非"您已参与过"
3. **check-then-act 竞态**: 幂等校验"先查再插"，依赖唯一索引兜底（当前安全但浪费一次查询）

## 四、当前阶段的已知缺陷

| 缺陷 | 影响 | 阶段二方案 |
|------|------|-----------|
| 无缓存，每次抢购查数据库 | 数据库压力大 | Redis 缓存活动信息 + 预扣减库存 |
| 无并发控制手段 | 依赖 SQL 原子性兜底，扩展性差 | 乐观锁/悲观锁对比 |
| 同步处理订单 | 响应时间长 | 消息队列异步（阶段四） |
| 订单过期无自动取消 | 库存被无效订单占用 | 任务调度（阶段五） |
| 密码明文存储 | 安全问题 | 阶段二顺带加密（BCrypt） |

## 五、下一阶段计划

### 阶段二：解决并发与性能（Redis 缓存 + 库存优化）
1. 引入 Redis: 活动信息缓存、库存预扣减（原子 DECR）
2. 全局异常处理器增加 DuplicateKeyException 分支
3. 幂等校验改为"直接插入，冲突即拒绝"
4. 密码加密（BCrypt）
5. 并发压测对比（目标: TPS 提升、响应时间下降）
