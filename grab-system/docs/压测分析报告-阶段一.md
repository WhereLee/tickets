## 二、压测分析

### 2.1 场景与结果

- 场景：100 并发同时抢购 activity=1（库存 100），Ramp-Up=0，循环 1 次
- 用户：${__Random(2,101)} 随机（100 个用户池）

| 指标 | 数值 |
|------|------|
| 吞吐量 | **61.9 req/s** |
| 平均响应 | **1189 ms** |
| P50 | 1217 ms |
| P90 | 1403 ms |
| P95 | 1436 ms |
| P99 | 1459 ms |
| 最小/最大 | 885 / 1459 ms |
| HTTP 错误率 | 0% |
| 业务成功 | **65 / 100（65%）** |
| 库存核对 | 100 - 65 = 35 剩余 ✅ **无超卖** |

### 2.2 关键洞察

**洞察 1：65% 业务成功率 ≈ 随机用户碰撞率，说明 35 个失败全是"重复抢购"而非"库存不足"**

```
100 次从 100 个用户池随机取，期望唯一用户数 ≈ 100 × (1 - (1-1/100)^100) ≈ 63.4
实际成功 65 个 → 高度吻合
```

**洞察 2：HTTP 错误率 0% 是假象**

- JMeter 的 success=true 只代表 HTTP 200
- 业务拒绝（"您已参与过该活动"）也返回 HTTP 200
- **真实业务成功率只有 65%**，压测必须结合数据库核对才能发现

**洞察 3：响应时间分布均匀偏大（885~1459ms），无长尾但整体慢**

- P50≈P90≈P95，说明所有请求都在排队，不是个别慢
- 根因：**所有并发请求串行排队等 `UPDATE activity` 的行锁**
- 100 个请求 × 每请求 4-5 次数据库交互 = 数据库成了唯一瓶颈

**洞察 4：压测验证了"防超卖"的兜底机制**

```
库存 100 → 订单 65 + 剩余 35 = 100 ✅
grab_record 65 条，无重复 (user_id, activity_id) ✅
```
真正防超卖的：`deductStock` 原子 UPDATE（`WHERE available_stock >= ?`）+ 事务回滚，而非代码里的库存检查。

## 三、问题根因链（从压测数据反推）

```
100 并发抢购
   ↓
每个请求 4 次数据库交互（查活动→查记录→扣库存→插订单→插记录）
   ↓
UPDATE activity 同一行 → InnoDB 行锁串行化
   ↓
所有请求排队等待 → 平均响应 1189ms，TPS 61.9
   ↓
同时暴露：并发下重复用户触发唯一索引冲突 → DuplicateKeyException
   ↓
未被业务异常捕获 → 返回"系统异常，请稍后重试"（用户体验差）
```

## 四、结论与阶段二目标

### 阶段一结论
1. **功能完整性**：✅ 业务闭环跑通，无超卖，无数据错乱
2. **边界性**：⚠️ 并发边界未真正测试（单测盲区），压测暴露了竞态
3. **并发能力**：❌ TPS 61.9，响应 ~1.2s，远达不到抢购场景要求
4. **效率**：❌ 数据库交互次数过多 + 行锁排队

### 阶段二可量化目标（对照基线）

| 指标 | 阶段一基线 | 阶段二目标 |
|------|-----------|-----------|
| TPS | 61.9 | ≥ 200（3 倍+） |
| 平均响应 | 1189 ms | ≤ 300 ms |
| 业务成功率 | 65% | ≥ 90%（消除重复碰撞导致的失败） |
| 数据库交互 | 4-5 次/请求 | ≤ 2 次/请求 |

### 阶段二方案（对应目标）
1. Redis 预扣减库存（原子 DECR）→ 库存判断不再走数据库行锁
2. Redis 缓存活动信息 → 减少查库
3. 幂等校验改"直接插入抢购记录，冲突即拒绝" → 消除 check-then-act
4. DuplicateKeyException 映射为业务错误 → 提示友好
5. 压测对比验证提升
