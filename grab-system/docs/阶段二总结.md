> 目标：解决阶段一极限压测暴露的三大瓶颈（行锁 / Tomcat 容量 / 连接池）
> 配置：目标服务器 4 核 3GB（Tomcat 200 线程 / 连接池 15 / JVM -Xmx1g）

## 三、关键结论

### 1. 稳定容量：100 → 200 并发（提升一倍）
- 200 并发 0 被拒 + 336ms，这是阶段二最重要的量化成果
- 阶段一 200 并发时 47.5% 请求被拒

### 2. 响应时间全面改善（行锁消除的直接结果）
- 100 并发：430 → 174ms（-60%）
- 500 并发：1301 → 459ms（-65%）
- 根因：抢购路径不再 UPDATE 库存行，只插自己的订单行（无锁竞争）

### 3. 被拒率在高并发档波动大（如实记录）
- 300~1000 档被拒率与阶段一互有高低，且同配置重复压测也有波动
- 原因：Ramp-Up=0 的"瞬间冲击"下，谁先建立连接有随机性；被拒率噪声大
- **结论：被拒率不能作为唯一指标；响应时间（稳定改善）+ 业务正确性（无超卖）才是硬指标**

### 4. 2000 档异常说明
- 1500 档被拒 92.7%，2000 档反而只有 24.7%——疑似 JMeter 客户端 2000 线程创建耗时，实际到达服务器的并发不足 2000，此档数据仅作参考

## 四、架构演变（这个项目的灵魂）

```
阶段一：数据库 available_stock 是真源
        UPDATE ... WHERE available_stock >= ?（原子防超卖）→ 行锁瓶颈

阶段二步骤4：Redis 预扣 + 数据库同步扣（两个源，需补偿）→ 拦截"抢不到的人"

阶段二步骤5：Redis 预扣真源 + 订单表最终记录 + DB 字段退化为展示值
        → 行锁彻底消失；Redis 丢失时用 total - 已售订单数对账重建
```

**核心认知**：库存字段从"被更新的变量"变成"算出来的投影"；订单表才是最终答案。

## 五、质量问题修复清单（步骤 7）

| 问题 | 修复前 | 修复后 |
|------|--------|--------|
| 并发重复抢购 | 返回"系统异常，请稍后重试"（DuplicateKeyException 未处理） | 400"您已参与过该活动"（唯一索引兜底 + 异常转换 + Redis 补偿） |

| 注册并发 | check-then-act 竞态 → 500 | 唯一索引兜底 → "用户名已存在" |

## 六、遗留问题与下一步方向

| 问题 | 说明 | 方向 |
|------|------|------|
| 高并发被拒（>200） | Tomcat 容量 200 线程是 4 核机器合理值，超出的拒绝是保护机制 | 限流（令牌桶）或横向扩容 |
| 抢购请求防刷 | 无限制，脚本可狂刷 | 限流 / 验证码 / 用户频率控制 |
| 订单过期未自动取消 | 30 分钟过期但无定时任务扫描 | 任务调度（阶段三） |
| 单点 Redis | Redis 挂了靠对账恢复，但恢复前拒绝服务 | 主从/哨兵（超出单机范围） |
| 幂等下单重试 | 用户重复点击同一次抢购 | 前端防重 + 服务端幂等键 |
