# 阶段二学习记录

## 步骤 1：认识 Redis（2026-08-23）

### 我学到了什么（大白话）
- Redis = 住在内存里的"超级快递柜"（key → value），本质是远程 HashMap
- 为什么快：内存（微秒级）vs 磁盘（毫秒级），快 100~1000 倍
- 数据结构：String（便利贴）/ Hash（表格）/ List（队列）/ Set（去重袋）/ ZSet（排行榜）
- 我们的场景只用 String，核心操作是 DECR（原子减）和 EXPIRE（过期）
- 关键：Redis 单线程处理命令 → 天然无并发问题 → 这就是它能替代数据库行锁的原因
- Redis 会丢数据（内存易失）→ 数据库永远是"真源"，Redis 只是加速器

### 我的疑问与解答
- 问：HashMap 是什么？
- 答：快递柜。存 = 放格子记取件码，取 = 输码直接开柜（不用翻找）。"哈希"= 把 key 搅拌成格子编号，key 不变编号不变。
- 问：为什么用 HashMap？和 SQL 什么关系？
- 答：查找 O(1) vs 数组 O(n)，数据越大差距越大。HashMap 是"内存层查找"，SQL 是"磁盘层查找"（MySQL 的 B+树索引也是同类思想）。程序先查内存（快）→ 没有 → 查数据库（可靠）→ 放回内存，这就是缓存。
- 问：Redis 是不是就是操作系统里的内存？
- 答：方向对（热数据留内存、冷数据清除——LRU/过期），但 Redis 不是"系统内存"，它是运行在系统上的一个程序，只是把数据存在内存里。系统管"所有程序怎么用内存"，Redis 只管"自己内存里存什么"。

## 步骤 3：活动信息缓存（Cache Aside 模式）（2026-08-23）

### 我学到了什么（大白话）
- Cache Aside 模式四步：读 = 先查缓存 → 命中返回；未命中 → 查库 → 回填缓存 → 返回；写 = 更新数据库 → 删缓存
- 为什么更新时删缓存而不是改缓存：删更简单可靠，下次读取自然重新加载；改缓存要考虑并发写，容易不一致
- 空值缓存（防穿透）：活动不存在也缓存 60 秒（NULL 标记），防止恶意遍历不存在的 id 直接打数据库
- 缓存过期时间权衡：太短防不住穿透，太长数据延迟大；正常信息 10 分钟，空值 60 秒（经验值）
- **序列化陷阱**：Jackson2JsonRedisSerializer 存对象只存数据不存类型，读出来是 LinkedHashMap 强转会报错；GenericJackson2JsonRedisSerializer 会在 JSON 里写 @class 字段还原类型
- **时间类型陷阱**：LocalDateTime 需要注册 JavaTimeModule 才能序列化，否则报 "Java 8 date/time type not supported"
- 设计决策：抢购流程查活动必须走数据库（需要实时库存），只有展示接口走缓存

### 验证结果
- ActivityCacheTest 3/3 通过：首次回填 + 二次命中且类型还原 / 空值缓存 / 实时与缓存互不影响
- 全量回归 23/23 通过（原有 20 个未被破坏）
- 接口实测：第 1 次查询后 Redis 出现 activity:1（带 @class 字段）；第 2 次命中缓存；不存在的 id 返回"活动不存在"且缓存 NULL 标记；TTL 验证 595 秒（10 分钟）/ 60 秒（空值）

## 步骤 5：抢购流程改造——库存概念的重新定义（2026-08-23）

### 我学到了什么（大白话）
- **核心思想转变**：阶段一/四认为"数据库库存字段是真源"；步骤 5 改为——抢购期间 Redis 是真源，订单表是最终记录，数据库 available_stock 退化为"展示兑底值"
- 为什么敢这么做："剩余库存"只有 Redis 需要实时知道（拦截请求）；"谁买到了"由订单表回答；数据库字段只是 total - 已售 的投影，随时能算出来
- 新流程：Redis 预扣（Lua）→ 建订单 + 记录（只插自己的行，无锁竞争）→ 不碰 activity 表！行锁彻底消失
- 对账重建：Redis 库存 key 丢失（如重启）→ total - 已售订单数（status IN (0,1)）恢复；订单表是真源所以随时能恢复
- 取消订单：改状态 + Redis INCR 加回；已取消订单不再计入已售（对账自然正确）
- 展示：详情接口用 Redis 实时库存覆盖 available_stock（不读数据库旧字段）

### 代码变更
- `OrderMapper`：新增 countSold()（SQL 聚合对账：SUM quantity WHERE status IN (0,1)）
- `StockService`：新增 hasKey() / getStock()
- `OrderService.grab()`：移除 deductStock 调用；库存 key 丢失时对账重建；cancel() 移除数据库库存回滚
- `ActivityService`：新增 getByIdWithStock()（缓存信息 + Redis 实时库存覆盖）
- `ActivityController`：详情接口改用 getByIdWithStock()
- 测试：cancel 测试改为验证 Redis 回滚；并发测试断言改为"数据库字段保持初始值"；新增对账重建测试

### 验证结果

## 步骤 4：Redis 预扣减库存（核心！写路径优化）（2026-08-23）

### 我学到了什么（大白话）
- 为什么 Redis 扣库存快：Redis 单线程执行命令 → 天然无锁竞争；内存操作微秒级（vs 数据库行锁 + 磁盘）
- 为什么需要 Lua 脚本："判断库存够不够 + 扣减"必须是一步原子操作，否则两个请求同时判断"够" → 都扣 → 超卖；Lua 脚本在 Redis 里整体执行，中间插不进其他命令
- 分工：Redis = 预扣（拦截抢不到的人，微秒级拒绝）；数据库 = 真源（最终数据，防 Redis 丢数据）
- 事务失败补偿：Redis 预扣成功但订单没建成 → INCR 加回（防止 Redis 扣了但库没扣）
- 幂等初始化：setIfAbsent 只在 key 不存在时写入（SETNX 思想）
- **重要洞察：预扣减解决的是"抢不到的人的等待"，不是"抢到的人的排队"**——成功者依然要排数据库行锁（O(库存) 次），这是步骤 5 要解决的

### 代码变更
- 新增 `StockService`：initIfAbsent（幂等初始化）/ tryDeduct（Lua 原子扣减）/ rollback（INCR 加回，key 丢失不重建）
- `OrderService.grab()`：加 Redis 预扣步骤；事务内失败 → catch 补偿 Redis；cancel() 加 Redis 回滚
- `run_scale.ps1`：重置库存时同步删除 Redis 库存 key（工具链升级）
- `RedisConfig`：序列化器换 GenericJackson2JsonRedisSerializer（@class 类型还原）+ 注册 JavaTimeModule

### 验证结果
- StockServiceTest 5/5：初始化幂等 / 扣减成功 / 不足不扣 / 回滚 / **100 线程抢 50 库存恰好 50 成功**
- OrderServiceConcurrentTest 1/1：**100 线程抢库存 50 → 50 成功 50 拒绝，DB 订单 50 + 记录 50 + 库存 0 + Redis 0**
- 全量回归 29/29 通过
- 接口实测：抢购 → Redis 4989→4988 → 取消 → 回滚 4989 ✅
- 压测对比：500 并发库存 100 → 订单 100 = 记录 100 = 库存 0（无超卖）✅
- **压测发现：库存充足（5000）时 100 并发无改善（481ms vs 阶段一 430ms）——因为预扣没拦截任何请求，数据库行锁依旧；预扣减的价值只在库存紧张时体现**

## 步骤 6：参数调优（按目标服务器 4 核 3GB）（2026-08-23）

### 我学到了什么（大白话）
- **参数要匹配部署目标**：Spring Boot 默认参数（maxThreads=200 / 连接池 10）本来就是为"4 核 2~4GB"典型服务器设计的；之前觉得"小"是因为拿 16 核本机压测
- 内存账本（3GB）：JVM 堆 1GB + 元空间 256MB + 线程栈 200MB（200×1MB）+ MySQL 500MB + Redis 100MB + 余量
- 线程数：纯计算=核数+1；IO 密集（等 Redis/MySQL）可远超核数，4 核标准 200 线程
- 连接池公式：核数×2+磁盘数≈9，取 15 留余量
- **min-spare-threads（预热线程）是瞬间冲击被拒的元凶**：默认 10，200 个请求瞬间到达时现场建线程来不及，accept 队列被挤爆
- 被拒不全是坏事：maxThreads=200 是 4 核机器的合理容量，超了拒绝是"保护机制"（宁可拒，不可雪崩）
- 冷启动干扰再验证：应用刚启动时 50 并发 2057ms，预热后 100 并发 184ms

### 代码变更
- `application.yml`：server.tomcat（max-threads=200 / accept-count=100 / min-spare-threads=50）+ hikari（maximum-pool-size=15 / minimum-idle=5）
- 启动命令：java -Xms512m -Xmx1g -XX:MaxMetaspaceSize=256m -jar ...

### 验证结果（对比默认配置，库存 5000）
| 并发 | 默认配置（步骤5） | 调优后 | 变化 |
|------|------------------|--------|------|
| 100 | 214ms / 0 被拒 | 184ms / 0 被拒 | 略快 |
| 200 | 317ms / 28.5% 被拒 | 413ms / 14.5% 被拒 | 被拒减半，吞吐提升 |
| 500 | 624ms / 33% 被拒 | 507ms / 28% 被拒 | 快 19% |
- 500 并发核对：订单 331 = 记录 331，Redis 4669 = 5000-331，无超卖
- 结论：目标 200 并发稳定（4 核 3GB 合理容量），超过部分被拒是保护机制
