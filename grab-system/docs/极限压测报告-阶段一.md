# 阶段一极限压测报告（阶梯加压）

> 目的：理解并发如何一步步压垮系统，找到每个瓶颈
> 条件：库存 5000（保证所有请求真实走完流程）、用户池 3000（避免重复干扰）、Ramp-Up=0（瞬间冲击）

## 二、性能曲线解读（大白话）

### 阶段 A：1~100 并发 —— 系统"能扛"，但每个请求要排队
- 1 并发：34ms（单事务真实耗时）
- 100 并发：430ms（12 倍劣化！）
- **根因**：所有请求抢**同一行**库存（`UPDATE activity`），InnoDB 行锁串行化——100 个事务排成一队，每人 34ms

### 阶段 B：200+ 并发 —— 开始"拒人"（Tomcat 容量极限）
- 200 并发：95 个连接被拒（47.5%），全部发生在**压测开始的 0-10ms**
- **根因**：Ramp-Up=0 的瞬间冲击下，Tomcat 需要把线程从 25 个（默认 min-spare）快速扩充到 200+，**线程创建速度跟不上连接到达速度**，accept 队列（100）被塞满后新连接被拒

### 阶段 C：500~800 并发 —— 连接池耗尽，响应恶化
- 500 并发：成功请求平均 **1301ms**（P99=2277ms）
- **根因**：HikariCP 连接池只有 **10 个连接**，大量请求在应用内排队等数据库连接；等连接 + 等行锁双重排队

### 阶段 D：1000+ 并发 —— "多拒少进"，吞吐反而下降
- 1000 并发：89% 被拒，只有 111 个进入应用
- **根因**：瞬时冲击被 Tomcat 挡掉大部分，进入的请求少 → 平均响应反而"好看"（633ms）
- **被拒率与进入量随机波动**（2000 并发时进入 445 个 vs 1500 时 131 个）——取决于 JMeter 线程建立连接的瞬间节奏

## 三、瓶颈定位（由内到外）

```
① 行锁串行化（数据库层）—— 从 1 并发就开始存在
   所有事务排队更新同一行库存，单事务 34ms → 100 并发时 430ms

② Tomcat 容量（应用层）—— 200 并发开始触发
   maxThreads=200 + acceptCount=100 = 300 容量，瞬时冲击超容量 → 连接被拒

③ 连接池 10（数据库访问层）—— 500 并发左右恶化
   10 个连接被占满，请求排队等连接 → 响应飙到 1.3s

④ JMeter 自身（压测工具）—— 1500+ 时开始可疑
   单机 2000 线程的开销可能影响压测准确性（需分布式压测验证）
```

**结论：系统真实极限 ≈ 100 并发**（0 拒绝、全部成功、响应 430ms 可接受）
超过 200 并发后：被拒 + 慢，体验不可用。

---

## 四、关键学习点

1. **单事务 34ms ≠ 高并发下的 34ms**：行锁把并发请求变成串行队列，100 个请求 = 430ms
2. **Ramp-Up=0 是"极限冲击"**：真实用户不会完全同时点击，但极限测试必须这样压才能暴露容量边界
3. **Tomcat 线程扩容有延迟**：min-spare-threads=25 → maxThreads=200，扩容期间新连接被拒
4. **连接池 10 是隐藏瓶颈**：Spring Boot 默认参数 ≠ 生产参数
5. **"平均响应"会骗人**：被拒请求不计入平均、业务拒绝也算 HTTP 200——**必须结合被拒率 + 数据库订单核对**
6. **压测前要预热**：冷启动（JIT）会让前几轮数据失真（50 并发那次 1029ms 是干扰）

## 五、对阶段二的启示

| 瓶颈 | 阶段二对策 |
|------|-----------|
| 行锁串行（根本瓶颈） | Redis 预扣减库存（DECR 原子操作），库存判断不走数据库行锁 |
| Tomcat 容量 | 调优 maxThreads/acceptCount，或引入限流让系统"优雅拒绝" |
| 连接池 10 | 结合压测调 HikariCP 参数（最大池大小、超时时间） |
| 响应 1.3s | Redis 前置后，事务内只做"建订单"（写路径），耗时大幅下降 |

**目标对比基线**：阶段二完成后，用同样阶梯（100/500/1000/2000）复测，对比：
- 被拒率是否下降
- 100 并发响应是否从 430ms 降到 100ms 内
- 系统极限从 100 并发提升到多少
