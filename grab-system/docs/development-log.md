### 问题 4: Tomcat 线程池/accept 队列满，请求被拒
- **类别**: 性能 / 容量
- **场景**: 500 并发压测
- **现象**: 84 个请求报 HttpHostConnectException（连接被拒），请求未进入应用
- **根因**: Tomcat 默认 maxThreads=200 + acceptCount=100 = 300 容量，500 并发超出部分被拒
- **解决**: 阶段二调优 Tomcat 参数（maxThreads/acceptCount），或引入限流保护
- **预防**: 压测前要了解服务器容量参数；生产环境需要监控线程池水位

### 问题 5: 数据库连接池（默认 10）成为隐藏瓶颈
- **类别**: 性能 / 配置
- **场景**: 100/500 并发压测
- **现象**: 成功请求平均 660ms（100 并发时 1189ms），大量时间花在等连接/等行锁
- **根因**: HikariCP 默认 maximum-pool-size=10，请求在事务期间持有连接，高并发时排队等连接
- **解决**: 阶段二配置连接池参数（结合压测数据调优），Redis 预扣减后事务时间缩短，连接占用时间大幅下降
- **预防**: Spring Boot 默认参数≠生产参数，必须结合压测调优

### 洞察: 500 并发平均响应反而更低的原因
- 库存 100 很快售罄，后续 316 个请求在库存检查阶段快速失败（事务几 ms），拉低了平均值
- 84 个连接被拒请求不计入响应统计
- **平均响应指标会被快速失败的请求掩盖，必须结合分位数和错误率看**

## 2026-08-23 阶段一 压测结果与问题

### 压测基线（阶段一）
- 工具: JMeter 5.6.3
- 场景: 100 并发抢购 activity=1（库存 100），Ramp-Up=0，循环 1 次
- 吞吐量: 61.9 req/s
- 平均响应: 1189 ms（最小 885 / 最大 1459）
- 错误率: 0%（HTTP 层）
- 业务结果: 100 请求 → 65 成功 / 35 拒绝（重复用户），库存 100 → 剩余 35 + 订单 65，**无超卖**

---

### 问题 1: 抢购接口响应慢，吞吐量低
- **类别**: 业务逻辑 / 性能
- **场景**: JMeter 100 并发压测 /order/grab
- **现象**: 平均响应 1189ms，TPS 仅 61.9；100 并发全部排队等数据库行锁
- **根因**: 每次抢购 4 次数据库交互（查活动 → 查抢购记录 → 扣库存 → 插订单 → 插记录），且并发请求全部串行等待 `UPDATE activity` 的行锁；步骤 5 的"检查库存"是多余的先查后扣，存在竞态但不致命（deductStock 的原子条件兜底）
- **解决**: 阶段二引入 Redis 预扣减库存 + 缓存活动信息，减少数据库交互
- **预防**: 压测是发现性能问题的必要手段，每个阶段都要做基线压测

### 问题 2: 并发下重复抢购返回"系统异常"而非友好提示
- **类别**: 业务逻辑
- **场景**: 两个相同 userId 的请求同时到达（JMeter 随机数碰撞模拟）
- **现象**: 步骤 3 查 grab_record 都没查到 → 双双通过 → 步骤 8 插入记录时唯一索引冲突 → 抛 DuplicateKeyException → 被全局异常处理器兜底为"系统异常，请稍后重试"
- **根因**: 先查后插存在竞态窗口；DuplicateKeyException 未被识别为业务异常
- **解决**: 全局异常处理器增加 DuplicateKeyException 分支（参照公司框架 SysLogAspect 的做法）；后续阶段用 Redis 预扣减/分布式锁彻底解决
- **预防**: 异常分类要完整，数据库唯一索引冲突应映射为业务错误

### 问题 3: 幂等校验依赖"先查再插"，存在竞态
- **类别**: 业务逻辑
- **场景**: 并发下同用户重复请求
- **现象**: 步骤 3 的 grab_record 检查与步骤 8 的插入不是原子的，靠唯一索引兜底
- **根因**: check-then-act 模式
- **解决**: 靠数据库唯一索引兜底是可行的（当前已生效），后续阶段可优化为"直接插入，冲突即拒绝"（insert 代替 select+insert），减少一次查询
- **预防**: 高并发场景优先用"唯一约束 + 冲突检测"而非"先查再插"

## 历史问题（阶段一开发过程中）

### 问题: PowerShell 命令执行 mysql 报错
- **类别**: 终端命令
- **场景**: 初始化数据库、查询数据时
- **现象**: `mysql -e "..."` 参数被 PowerShell 吞掉、`<` 重定向不支持、`&&` 不支持
- **根因**: PowerShell 与 cmd 语法差异；内联引号被解析器剥离
- **解决**: 复杂命令一律写成 .bat / .ps1 脚本文件执行（参考 powershell-safe-command 技能）
- **预防**: 涉及引号嵌套、多语句、中文的命令禁止内联执行，必须写脚本文件

### 问题: MySQL 服务未启动
- **类别**: 环境
- **场景**: 首次运行单元测试
- **现象**: `Can't connect to MySQL server on 'localhost:3306' (10061)`
- **根因**: MySQL80 服务处于停止状态
- **解决**: 用户手动通过 services.msc 启动
- **预防**: 运行测试前先 `Get-Service *mysql*` 确认服务状态

### 问题: 测试数据中文写入 MySQL 乱码/超长
- **类别**: 编码
- **场景**: 通过 PowerShell 管道导入 init.sql
- **现象**: `Data too long for column 'title'`、中文变 `???`
- **根因**: PowerShell 管道默认编码与 UTF-8 不一致
- **解决**: SQL 文件用 UTF-8 保存，经 .bat 文件执行；测试数据临时用英文
- **预防**: 含中文的 SQL 一律走文件方式执行，并显式指定编码

### 问题: Java 8 不支持 var 关键字
- **类别**: 编译
- **场景**: 单元测试中 `var orders = ...`
- **现象**: `找不到符号: 类 var`
- **根因**: pom.xml 的 java.version=1.8
- **解决**: 项目升级 Java 17（用户指定），测试代码改为显式类型
- **预防**: 项目使用 Java 17，语法特性按 17 标准
